🔑 Integrity Constraints

  • users $\rightarrow$ donors: 1 : 0..1 with ON DELETE SET NULL. Donor profiles persist if user login accounts are purged.
  • donors $\rightarrow$ donations: 1 : 0..* with ON DELETE RESTRICT. Preserves clinical audit history; donors with recorded donations cannot be deleted.
  • blood_stock units: Guarded by CHECK (units >= 0) and application-level transactions.

⚙️ Transactional Business Logic

  • Donation Intake: When POST /api/donations is logged, it increases blood_stock.units and updates donors.last_donation_date.
  • Request Fulfillment: When POST /api/requests/:id/fulfill is approved, the system verifies sufficient stock and atomicity decrements inventory.

👥 Actor Catalog

  • Guest / Public: Can browse blood availability, submit public donor applications, or request emergency blood.
  • Registered Donor: Has a JWT session, can update availability status and personal contact details.
  • Registered Requester: Can track personal request statuses (/requests/mine).
  • Employee / Staff: Manages daily intake donations, approves/rejects requests, fulfills verified orders.
  • Administrator: Superuser with destructive capabilities (delete donor, delete request, override stock).

🔗 UML Relationships

  • Generalization: Admin inherits all use cases of Employee.
  • <<include>>: Fulfilling a blood request or recording a donation always includes stock adjustment.
  • <<extend>>: Registering as a donor optionally extends to creating a user login account with password.
